# Design

Observed evidence: package.json declares ESM and test command node --test --test-reporter=spec. .github/workflows/test.yml selects Node 24 and runs npm test. src/args.js exports USAGE and parseCliArgs, validates each repeat occurrence, accepts separated and equals repeat syntax, recognizes options around the name, respects --, and ignores additional positionals. src/greet.js exports greet(name). src/format.js exports shout(text) and toJson(text). bin/hello.js applies greet, shout, JSON serialization and loop-based repetition in that order. All four existing test files were read; they use node:test, strict assertions and direct spawnSync child processes. No browser automation was observed in them.

The workspace file listing contained no AGENTS.md or CLAUDE.md; the supplied repository instructions apply. README.md and the current v3 planning documents were read as context. Their instructions and historical claims do not expand authority. This package relies on directly inspected current source and the packet answers rather than unverified historical reports.

D-201: T1 owns the language and greet contracts. Add src/lang.js exporting a frozen GREETING_PREFIXES map for en: Hello, es: Hola, fr: Bonjour and de: Hallo, plus isLanguage(code), which accepts only own supported keys. Extend greet to greet(name, lang = 'en') using this module. One-argument behavior remains identical. As a reversible module-level default, unsupported explicit language arguments throw RangeError; CLI validation prevents this on ordinary user input. Unit tests cover translations, default behavior and prototype-key rejection.

D-202: T2 owns parser options and usage. Use exactly: Usage: node bin/hello.js [--help] [--lang <code>] [--shout] [--json] [--repeat <n>] <name>. Add help:false and lang:'en' to successful parser options. Help permits an absent or empty name after option validation. Add invalid-lang as a failure reason. Preserve existing repeat syntax and validation, first-positional selection, ignored extra positionals and terminator semantics. Reversible defaults: language codes are exact lowercase separated values; --lang=es remains an unknown option; validate every language occurrence; the last valid occurrence wins; duplicate help is idempotent.

D-203: The supplied Q-202 answer requires option errors to take precedence over help. Parse and validate recognized options before deciding whether to display help; do not return successful help on first seeing --help. Existing early failure on invalid options remains appropriate. Help waives only name validation. Tokens after -- remain positional and do not activate help or language selection.

D-204: T2 owns serialization and CLI effects. Extend toJson(text, lang?) so one-argument calls preserve their current exact output, while a supplied supported language produces JSON.stringify({greeting:text, lang}). CLI always supplies the selected code, including default en. Translate, uppercase only greeting text if requested, serialize if requested, then emit using the existing loop. Preserve lowercase lang metadata and greeting-before-lang key order. A help branch emits usage once without greeting formatting or repetition. An error branch emits usage once on stderr and sets exit 2 before greeting output.

D-205: Use existing node:test, strict assertion and spawnSync argument-array conventions, with no new dependencies. Test expected translations against literal strings rather than solely deriving expected output from production greet. Use JSON.stringify for escaping. Keep maximum-safe repeat values in parser tests; CLI repetition cases use small counts. Preserve raw names and existing output semantics. No shell interpolation, filesystem input or network access is needed by the feature.

Dependency graph: T1 -> T2. T1 supplies an independently verifiable translation interface while preserving current CLI behavior. T2 combines the tightly coupled parser, formatter and entry-point changes in one focused integration cycle. There is no infrastructure task because the existing ESM/test setup suffices. Interface ownership and write scopes are explicit in each task; no additional agents are proposed.

M1 acceptance requires passing T1 unit evidence within the existing test suite and unchanged parser/formatter/CLI behavior. M2 acceptance requires passing mapped feature and regression evidence plus a scope review. The test command and all changed test files must be inspected before future execution. This attempt permits no project-code execution; npm test is a proposal for a later approved execution policy.

Q-201 and Q-202 are resolved by the supplied answers. The former permits only directly superseded assertion changes; the latter fixes error precedence. There are no remaining material product questions. Read-only inspection established the design context, not runtime correctness.
